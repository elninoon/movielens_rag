# MovieLens 电影推荐 RAG

根据用户的训练历史，从教师脚本给出的 100 部候选电影中推荐 10 部，使用 Qwen 输出排序、中文理由和可追溯依据。本项目实现热门推荐基线、RAG 和移除检索证据的消融，使用同一组验证用户进行评测。

作业要求与数据规则分别见 [要求与验收](docs/requirements.md) 和 [数据协议](docs/data_protocol.md)。报告及约 10 分钟汇报材料放在 `deliverables/`，正式实验数据与结果仅在本机保存。

当前正式实验已结束：官方数据完整审计通过，30 项测试通过。RAG 的 30 位用户均成功；消融成功 29/30，用户 921 两轮返回候选外或历史已看电影，作为真实约束遵循失败保留并计零。三种方法均使用固定 30 位用户分母，没有为获得成功结果重复抽样。模型服务权限已恢复；此前 18 份 HTTP 403 开发错误保留在 `outputs/formal/errors/`，成本单独记录，不计为最终推荐失败。

| 方法 | 成功用户 | Recall@10 | NDCG@10 |
| --- | --- | --- | --- |
| 热门基线 | 30/30 | 0.335556 | 0.273426 |
| RAG | 30/30 | 0.483889 | 0.346630 |
| 移除检索证据 | 29/30 | 0.262222 | 0.243269 |

最终材料按上述真实实验结果生成到 `deliverables/`：`MovieLens_RAG_报告.md`、`MovieLens_RAG_报告.pdf` 和 `MovieLens_RAG_汇报.pptx`。成员姓名按用户要求暂不填写。

> GitHub 公开仓库包含代码与说明；`data/`、`outputs/`、`deliverables/` 和本机 `.env` 不随仓库上传。文中这些路径指本地实验目录；报告和汇报材料由组内课程渠道共享。队友首次运行需按下文准备数据，并使用自己的 API 配置。

## 给组员的阅读指南

第一次接触 RAG，建议先读下面的「完整流程」，再查看「运行与复现」。已有实验已经完成，查看报告和演示不需要重新调用模型。想核对实现时，按 `scripts/prepare_movielens.py → data.py → retrieval.py → generation.py → grounding.py → evaluation.py` 的顺序阅读，后五个文件都在 `src/movie_rag/` 中。

## 完整流程：从评分记录到十部推荐

### 1. 先理解任务和 RAG

本项目的输入是一个用户过去的评分记录，以及指定的 100 部候选电影；输出是按适合程度排列的 10 部电影，每部带中文理由和依据。电影必须来自候选集合，而且不能是历史中已经看过的电影。

RAG 是 Retrieval-Augmented Generation，即「检索增强生成」。可以把它理解为开卷作答：程序先整理与用户有关的资料，再把资料连同题目交给大模型，让它有依据地推荐。这里的「检索」是在课程数据中找证据，不会上网搜索，也没有训练或微调一个新的大模型。

本项目分工如下：

| 部分 | 做什么 | 本项目实现 |
| --- | --- | --- |
| 数据准备 | 把原始电影与评分整理成输入和评测答案 | 教师准备脚本、`DataStore` |
| Embedding（文本向量化） | 把用户偏好和电影资料转换成可比较的数字数组 | `text-embedding-v4`，默认 1024 维 |
| Rerank（重排） | 同时比较偏好描述与电影资料，重新判断相关程度 | `qwen3-rerank` |
| 近邻评分 | 查看历史口味相似的其他用户如何评价候选电影 | 本地 NumPy 计算 |
| 生成 | 阅读全部输入，决定最终推荐与顺序 | `qwen3.8-27b` |
| 校验与理由整理 | 检查输出是否合法，把理由落实到真实字段 | 本地程序 |
| 评测 | 用事先藏起来的评分检查推荐效果 | 独立评测模块 |

```text
MovieLens 原始电影表、评分表
    ↓ 教师脚本：解析字段、划分历史和留出评分
电影资料 + 训练评分 + 每位用户的历史与100候选
    ├─ 训练评分 → 电影统计 + 相似用户评分
    └─ 用户历史 → 偏好查询；候选资料 → 电影文档
                         ↓
           全部候选的向量相似度 + Rerank 相关度
                         ↓ 与相似用户支持融合
                    前30条增强证据
                         ↓
完整历史 + 全部100候选 + 30条证据 → Qwen → 10部推荐
                         ↓
              输出校验 → 理由整理 → 保存结果
                         ↓
        独立读取留出标签 → 评测、失败分析、报告
```

### 2. 数据生成：准备的是实验数据，不是让模型编造数据

实现：`scripts/prepare_movielens.py`。

1. 下载官方 MovieLens 100K 压缩包及 MD5 文件，并校验压缩包是否正确。也可以指定已有压缩包。
2. 读取 `u.data`：每条记录包含用户编号、电影编号、1～5 分评分和时间戳。
3. 读取 `u.item`：提取电影编号、片名、上映日期和类型。原始类型用一组 0/1 标记表示，例如某电影的 Comedy、Romance 为 1，就转换成这两个类型名称。
4. 将每位用户的评分按时间戳、电影编号升序排列。从至少有 20 条评分、最后 5 条中至少有一条 ≥4 分的用户中，使用固定种子 `20261018` 随机选出 30 位验证用户。
5. 对这 30 位用户，藏起最后 5 条评分，之前的记录作为可见历史；其余用户的评分全部保留在训练集中。
6. 对每位验证用户，把藏起的 5 部电影与随机抽取的 95 部该用户从未评分的电影混合并打乱，形成 100 部候选。95 部未评分电影只是评测中的对照候选，未评分不能直接解释为用户不喜欢。

原始数据共有 1,682 部电影、943 位用户、100,000 条评分。划分后训练评分为 `100,000 − 30 × 5 = 99,850` 条，留出评分为 150 条。

「藏起」指评分和历史身份不提供给推荐流程；这 5 部电影的公开元数据仍作为普通候选输入。留出评分中 ≥4 分的电影才是评测要找回的相关电影，因此每位用户的答案数为 1～5 部，不固定为 5 部。

这是按验证用户各自的历史切分，其他用户没有统一的时间截点；讲解时不要称为全局时间切分。

### 3. 结构化：让电影、用户历史和评测答案各有明确位置

生成的数据在 `data/movielens_dev/`：

| 文件 | 结构与内容 | 谁会使用 |
| --- | --- | --- |
| `movies.csv` | 每行一部电影：`movie_id, title, release_date, genres`；多类型用 `|` 分隔 | 数据加载、检索 |
| `train_ratings.csv` | 每行一次训练评分：`user_id, movie_id, rating, timestamp` | 电影统计、近邻计算 |
| `validation_cases.jsonl` | 每行一位验证用户：`user_id`、历史 `history`、100 部 `candidates` | 推荐输入 |
| `validation_labels.jsonl` | 每行一位用户的留出评分 `heldout` 和相关电影编号 `relevant_movie_ids` | 独立评测 |
| `split_manifest.json` | 种子、所选用户编号、数据来源和校验信息 | 核对实验划分 |

CSV 适合存统一列的表格；JSON 能表达「用户下面有多条历史、多个候选」这样的嵌套结构；JSONL 就是一行一个 JSON 对象。一个 case 是一次推荐任务，核心结构如下。以下是缩略的虚构示例，真实输入包含全部历史和 100 部候选：

```json
{
  "user_id": 123,
  "history": [
    {"movie_id": 10, "title": "示例历史电影", "genres": ["Comedy"], "rating": 5, "timestamp": 1000000000}
  ],
  "candidates": [
    {"movie_id": 20, "title": "示例候选电影", "release_date": "01-Jan-1995", "genres": ["Comedy", "Romance"]}
  ]
}
```

候选中没有这个用户对候选电影的真实评分。`DataStore` 加载 CSV 时把编号、评分转换成整数，把类型拆成列表，并建立三个便于查询的索引：每部电影的评分列表、每位用户的电影评分表、每部电影获得 ≥4 分的次数。这些统计只使用训练评分。

这里的「训练集」用于提供历史和统计，本项目不会用它更新三个远程模型的参数。

### 4. 构造检索资料：一份用户偏好描述、一部电影一份文档

实现：`retrieval.py` 的 `_profile()`、`_document()`。

**用户查询（query）**：程序从全部可见历史计算各电影类型的平均评分与记录数，再列出最多 8 部高分电影（≥4 分）和最多 5 部低分电影（≤2 分）。高分记录按评分高者优先、同分较新者优先；低分记录按评分低者优先、同分较新者优先。最后组成一段英文偏好描述，供向量模型和重排模型使用。

例如，历史中喜剧平均分较高、恐怖片平均分较低，查询会把这两类倾向及具体影片列出来。多类型电影会参与各自类型的统计。类型平均分是偏好线索，不意味着用户必然喜欢所有同类电影。

**电影文档（document）**：一部候选电影对应一小段文本，包括编号、片名、上映日期、类型、训练评分数量、训练平均分、≥4 分的次数。没有训练评分时明确写明。文档不包含额外编写的剧情、演员或影评。

这份资料本来就是一部电影一条短记录，所以没有对长文章做切块（chunk）。也没有额外部署向量数据库：当前用本地 JSON 缓存向量，用 NumPy 比较向量。

### 5. Embedding 检索：把文字变成可比较的数字

实现：`_vectors()`、`retrieve()`。

Embedding 模型把每段文本变成一个默认含 1024 个数字的向量。可以理解为给文字生成一组用于比较语义的坐标；单个维度没有在本项目中被定义为「喜剧程度」或「悬疑程度」。

程序分别向量化用户偏好查询和全部未看候选的电影文档，将向量归一化，再用点积得到余弦相似度（`dense_score`）。分数越高，表示模型认为电影资料与偏好描述越接近。它衡量的是文本匹配程度，不是预测用户会打几分。

电影文档可能被多个用户共用，因此向量会缓存在 `cache/embeddings_*.json`。缓存身份绑定模型、维度、服务地址、文本及文本类别；缺失的文本才重新请求，每批最多 10 条。清理缓存后，后续实际需要计算向量时会重新生成并产生 API 调用。

注意本项目的候选只有 100 部，因此向量阶段给全部候选打分，并不先截取一小部分再交给 Rerank。

### 6. Rerank：直接阅读偏好与电影资料，再评一次相关程度

实现：`client.py` 的 `rerank()` 和 `retrieval.py` 的 `retrieve()`。

向量匹配先把两段文字各自转换成数字，再比较距离；Rerank 则把用户查询和候选文档一起交给重排模型，获得每个候选的 `relevance_score`。它负责给资料判相关度，不负责生成最终推荐理由。

当前实现把全部候选文档交给 `qwen3-rerank`，请求返回全部候选的分数。返回的 `index` 对应传入文档列表的位置，程序据此映射回电影编号，并检查索引、分数以及是否完整返回。

Rerank 分数随后参与融合，不能直接把它当成最终推荐排名，也不能把它解释为真实评分或喜欢概率。

### 7. 加入相似用户：不只看类型，也参考共同评分习惯

实现：`_neighbors()`。

这一部分是协同过滤思路：如果两个人过去对电影的评价比较一致，那么其中一个人对新候选的评价，可以为另一个人提供参考。

1. 使用训练评分构造「用户 × 电影」矩阵。已评分值用 `(评分 − 3) / 2` 转换，即 1 分对应 −1，3 分对应 0，5 分对应 1；未评分位置也为 0。
2. 对目标用户的可见历史使用同样的表示，计算与各训练用户的余弦相似度，排除自己，保留相似度为正的前 40 位用户。
3. 对每部候选，汇总这些近邻的真实训练评分：

   `cf = Σ[相似度 × (评分 − 3) / 2] / (Σ相似度 + 2)`

   求和仅包括评价过该候选的近邻。分母额外加 2，使少量评分给出的支持更保守；没有支持时结果为 0。
4. 每部电影最多保存前 5 条近邻评分供核查；计算分数时使用选出的最多 40 位近邻中所有对该片有评分的人，不只使用展示的 5 条。

这个分数表示近邻的支持方向与强度。检索文档和近邻计算都不读取目标用户的留出评分。

### 8. 融合排序：从 100 部候选中挑出 30 条增强证据

默认融合公式为：

```text
semantic = (余弦相似度 + 1) / 2
cf_scaled = (近邻支持分数 + 1) / 2
综合分数 = 0.45 × Rerank分数 + 0.35 × cf_scaled + 0.20 × semantic
```

这相当于结合三种线索：重排模型对文字的判断、相似用户的评分、向量语义匹配。权重是项目预设配置，没有通过留出标签训练这些权重。无近邻支持时 `cf=0`，换算后为 0.5，表示该信号处于中性位置。

程序按综合分数降序排列，同分按电影编号升序，取默认 `top_k=30` 条证据。每条证据包括 `movie_编号`、电影资料、各项分数、近邻评分、训练高分次数和来源文件名，保存到 `outputs/实验名/retrieval/用户编号.json`。

**30 指增强证据条数，10 才是最终推荐条数。** 这 30 部有额外统计与近邻证据；未进入前 30 的候选仍会以基本资料的形式提供给生成模型。

若使用 `--no-rerank`，融合变为 `0.65 × semantic + 0.35 × cf_scaled`。这与后面的 `no_retrieval` 消融不同：前者仅关闭重排，后者移除全部增强证据。

### 9. 生成：把历史、候选和证据交给 Qwen

实现：`generation.py` 的 `build_messages()`、`recommend()`。

生成输入由两部分组成：系统提示词说明规则；用户消息提供结构化资料：

| 输入 | 提供什么 | 引用编号 |
| --- | --- | --- |
| `history` | 全部可见训练历史，不只查询中列出的 8 部高分、5 部低分电影 | `history_电影编号` |
| `candidates` | 全部 100 部候选的基本资料 | `candidate_电影编号` |
| `retrieved_evidence` | 默认 30 条经过融合排序的增强证据 | `movie_电影编号` |

系统提示词要求：仅从候选选 10 部不同电影，不推荐已看电影；按匹配程度排序；理由使用中文并引用存在的证据；不能补充数据中没有的剧情、演员或影评。每条推荐必须引用自身的候选编号。

Qwen 根据这些输入决定选哪些电影、排什么顺序，并返回 JSON，例如 `movie_id`、`rank`、`reason`、`evidence_ids`。检索综合分数只提供证据顺序，不直接决定这 10 部的最终排名。

生成配置为温度 0、固定种子 `20261018`、最多 5000 个输出 token、关闭 thinking。温度和种子有助于减少波动，但服务端输出仍可能有非确定性。

### 10. 校验和理由整理：让最终结果可用、可核查

**第一步：校验模型返回值。** 检查 JSON 能否解析、是否恰好 10 部、编号是否属于候选且没有看过或重复、排名是否连续 1～10、理由是否非空、引用是否存在且包含该片自身的候选依据。若失败，将具体错误反馈给模型，最多再生成一次；两轮仍不合法则记为失败。网络请求层另有重试机制，与这两轮内容校验不同。

提示词中有「理由最多 80 个汉字」的要求，但当前程序没有对字数作硬校验。引用编号合法也不等于原始理由语义一定正确，因此还要整理理由并保留原始输出。

**第二步：用真实字段生成最终理由。** `grounding.py` 保留模型选出的电影和排名，仅整理说明文字：

- 从输入历史中寻找评分 ≥4、与候选有共同类型的影片；优先使用模型已引用的有效历史，再考虑共同类型数量、评分和时间。
- 找到支持时写明「你给某片评了几分，本片与它有什么共同类型」；找不到则明确作为探索项推荐。
- 只有模型引用了该候选对应的检索证据，才附加其训练高分次数。
- 将模型原始理由保存在 `model_reason`；最终理由存入 `reason`；原始请求和响应保存在 `attempts`。

例如，若历史中确有一部喜剧被用户评为 5 分，候选也是喜剧，最终理由可以说明这项类型匹配。它不会把 3 分改写成高分，也不会自行补出剧情。这种理由说明了可核查的推荐依据，但不能完整还原模型内部为什么这样排序。

### 11. 保存、对照评测与报告

正式实验目录 `outputs/formal/` 中的子目录各有分工：

| 路径 | 内容 |
| --- | --- |
| `popular/` | 热门基线：按训练集 ≥4 分次数推荐，不调用生成模型 |
| `retrieval/` | 每位用户的查询、增强证据、分数与检索调用记录 |
| `rag/` | 使用增强证据的生成结果、理由、原始输出与调用记录 |
| `no_retrieval/` | 去掉增强证据的对照结果；仍提供完整历史和全部候选 |
| `errors/` | 续跑前归档的失败记录，保留过程与成本依据 |
| `config.json` | 模型、用户集合、参数及实验身份 |
| `evaluation.json` | 各方法汇总与逐用户指标 |
| `failure_cases.json` | 真实漏推荐案例及证据覆盖分析 |

同名同配置实验会复用已保存结果、检索文件和向量缓存；更改数据、主要实现或配置后应使用新的实验名。仅查看现有结果不需要重新调用模型。

全部推荐保存后，评测模块才读取 `validation_labels.jsonl`。两项主要指标为：

- **Recall@10（召回率）**：藏起且评分 ≥4 的电影中，最终找回多少。例如相关电影有 4 部，推荐命中 2 部，召回率为 `2/4=0.5`。
- **NDCG@10（排序质量）**：不仅看是否命中，还奖励把命中的相关电影排在靠前位置，并相对于理想排名归一化。

程序还统计至少命中一部的比例（HitRate）、10 条中命中的比例（Precision）和首次命中位置的倒数（MRR）。各用户的指标分别计算后取平均，正式实验三种方法都以同一组 30 位用户比较，失败或非法输出计零。评测代码会单独报告并排除无有效标签的用户；本次划分确保每位用户都有至少一部相关电影，不涉及这种排除。

`no_retrieval` 用来观察额外检索证据是否有帮助：它保留相同的历史、候选、生成模型、系统规则和理由整理步骤，仅移除 `retrieved_evidence`。当前结果见文首表格。报告 PDF、Markdown 和汇报 PPT 放在 `deliverables/`，不需要重新运行实验就能阅读。

### 12. 组员可以按这个顺序检查一个真实案例

1. 从 `split_manifest.json` 找到一个用户编号，在 `validation_cases.jsonl` 看他的历史和候选。
2. 打开 `outputs/formal/retrieval/该编号.json`，看 `query` 如何概括偏好，以及前 30 条证据的分数、来源和近邻支持。
3. 打开 `outputs/formal/rag/该编号.json`，看最终 10 部电影及 `reason`，再对照 `model_reason`、`evidence` 和 `attempts`。
4. 对照同编号的 `no_retrieval/`、`popular/`，理解不同方法选了哪些电影。
5. 最后查看标签和评测中的逐用户指标，分析相关电影是没进增强证据，还是进了证据却没有被最终选中。由于全部候选始终可见，没进入增强证据不代表模型完全看不到该片。

## 方法与评测

检索库由电影元数据和训练集评分统计组成，不添加剧情或影评。用户查询使用全部历史的类型均分，并列出至多 8 部高分和 5 部低分电影。候选电影文档由真实 Embedding 模型转为向量，使用余弦相似度；Rerank 对候选文档重排，并结合仅由训练评分计算的近邻支持，选取前 30 条证据交给 Qwen。具体分数及近邻信息随证据保存，模型不会把预测分数当作真实评分。

Qwen 同时看到完整历史、全部候选和检索证据，可从全部候选中推荐。每条推荐必须引用其候选元数据，引用的历史或检索证据必须真实存在。结果校验负责格式、编号、数量、去重和证据编号；理由与证据在语义上是否一致仍须检查真实样例，不能仅凭引用编号有效就断言没有幻觉。

最终理由使用 `grounding.py` 的确定性证据渲染：保留 Qwen 选出的电影和顺序，优先查找模型引用且评分 ≥4、与候选具有共同类型的真实历史，明确展示片名、实际评分及共同类型；找不到支持时标明探索推荐。仅在已引用的对应检索证据存在时补充训练高分次数。模型原始理由保存在 `model_reason`，原始响应与提示词保存在 `attempts`，便于检查把 3 分说成高分等问题。RAG 和移除检索的消融使用同一理由规则，该步骤不改变推荐排名。该规则已接入生成流程；此前 42 份旧结果统一迁移，后续生成自动应用，最终 59 份成功输出均使用同一规则，电影与排名完全未改。报告区分模型排序、原始模型理由和最终渲染理由。

`python scripts/finalize_reasons.py` 仅用于把旧流程已保存的 `outputs/formal/` 结果迁移到该理由规则，无额外参数。本次迁移已执行；常规实验和续跑无需再执行该脚本。

评测输出 Recall@10、NDCG@10、HitRate@10、Precision@10、MRR@10 和输出合法性等信息。缺失、调用失败或非法推荐的用户不会被静默丢弃，而是计零并记录问题。报告比较同一组用户及候选，并分析至少 3 位失败用户，区分检索遗漏、生成排序及偏好与理由问题。

标签只在推荐完成后的独立评测阶段读取。推荐提示词、Embedding、近邻统计和热门次数均不使用 `validation_labels.jsonl` 或留出评分。
